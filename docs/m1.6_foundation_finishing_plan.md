## 1. Why this sprint exists

M1.5 closed sprint-wide 6-agent QA + Commit 39 fix-pass + verification report.

M1.6 closes all three categories on a sealed foundation before M3 visual

## 4. Pre-sprint finding — D11 drift between strategy doc and Rust backend

A cross-repo agent sweep on `quilty-aws/` surfaced a doc-vs-code drift that
needs reconciliation before any further auth-shaped work compounds it:

| Source                                | Claim                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Strategy doc D11                      | "Rust-backend-issued `quilty_sub` UUID supersedes `cognito_sub` as the cross-service user identifier" |
| Strategy doc D11 rationale            | Future identity-provider swap leaves downstream code untouched                                        |
| `quilty-aws` post_confirmation Lambda | Does **NOT** mint a separate `quilty_sub`. The Cognito `sub` IS the canonical user identifier.        |
| `quilty-aws` DynamoDB `quilty_main`   | User row PK = `USER#{sub}` where `sub` is the Cognito sub                                             |
| `quilty-aws` Rust crates              | `quilty-core/src/identity.rs` newtype `Sub` wraps the Cognito sub; treats it as canonical             |
| `quilty-aws` `TenantId` newtype       | Reserved (Wave 5 B3 / G4) but hard-coded to `TenantId::DEFAULT = "default"`                           |

The code is internally consistent (single-tenant consumer auth, Cognito sub
as canonical identifier) but the strategy doc claims an indirection that
doesn't exist. This is the canonical doc-drift failure mode — both are
defensible designs, but the canonical claim must match the code.

**Decision needed in M1.6:** pick one and update the other.

- **Option A (recommended — match doc to code):** Update D11 to say "Cognito
  `sub` IS the canonical user identifier across web + mobile + backend; a
  future Cognito swap is a one-time user-ID remapping migration, not a
  daily-running indirection." Cheap, matches reality, removes the
  swap-resilience claim that isn't backed by code.
- **Option B (build the indirection):** Add `quilty_sub` minting in
  post_confirmation, add a `cognito_sub → quilty_sub` mapping field on
  `UserProfile`, propagate `quilty_sub` everywhere. Multi-day Rust work,
  zero present value, pays back only if Cognito gets swapped (low probability
  given Plus-tier commitment + WebAuthn rpId binding).

The recommendation is **Option A** — the reservation that already exists
(`TenantId` newtype, `external_idp_id` schema attribute, `quilty-m2m-partner-reserved`
client) carries the swap-resilience optionality far better than a parallel
identifier ever could.

## 5. Workstream A — Cleanup sweep (~5h)

The 6 items the post-M1.5 fresh-eyes audit surfaced. Sequential, all in one
commit at the head of the sprint so the rest of M1.6 starts on a clean tree.

### A.1 — `sst.config.ts` `$site` forward-ref runtime bug (1h)

`sst.config.ts:203` reads `$site?.url ?? ''` inside the same `Nextjs`
constructor that produces `$site`. At runtime, that expression always
evaluates to `''` because `$site` is undefined when the constructor argument
is being evaluated. For non-`dev` stages (every PR preview) this ships
`NEXT_PUBLIC_SITE_URL=''` to the Lambda — every absolute URL in metadata
canonical/OG/JSON-LD falls back to `http://localhost:3000`.

**Fix:** move the env-var assignment into the `transform.cdn` callback (which
receives the resolved domain post-creation), OR drop preview-stage support
for `NEXT_PUBLIC_SITE_URL` and document the limitation. The transform-callback
path is the right choice — preview stages are a real validation surface and
need real URLs.

### A.2 — `packages/rate-limit/coverage/` committed to source (15min)

Coverage report artifacts (`base.css`, `block-navigation.js`,
`coverage-summary.json`, etc.) are in the source tree. `.gitignore` miss.

**Fix:** `git rm -r packages/rate-limit/coverage/` + add `packages/*/coverage/`
to root `.gitignore` + the same to per-package `.gitignore` if any package
ships its own.

### A.3 — `.bak` files in `.claude/hooks/` and `.claude/settings.json` (15min)

`guard-bash.sh.20260526-023824.bak` and `settings.json.20260526-023824.bak`
are tracked dirty files from a recent harness edit.

**Fix:** Decide — either commit the harness change cleanly (then delete the
`.bak` files), or revert the harness changes and delete `.bak`. Cannot edit
`.claude/` from inside Claude itself per the `guard-write.sh` hook; user
manually applies the chosen action.

### A.4 — PostHog/Amplitude drift walk (2h)

The 2026-05-19 pivot reverted D42b from PostHog to Amplitude. Most of the
source migrated; some surfaces still carry PostHog identifiers as
defense-in-depth and need an explicit decision:

- `eslint.config.mjs` `VENDOR_SDK_IMPORTS` lists `posthog-js` and
  `posthog-node` — keep as defense-in-depth (zero cost) and document the
  rationale inline, OR remove and rely on the general no-restricted-imports
  rule. **Recommend: keep**, with a one-line comment that the post-pivot
  defense-in-depth includes never-shipped vendors.
- `next.config.ts` `transpilePackages` + `experimental.optimizePackageImports`
  lists: verify both lists match the actual workspace package set; either
  list could be silently stale.
- Strategy doc Open Questions + trigger watchlist: verify the PostHog
  reference is consistent.

Output: a one-line entry in the strategy doc update log + a per-file
sweep commit.

### A.5 — ESLint compliance tests misplacement (1h)

`apps/web/__tests__/eslint-compliance-rules.test.ts` and
`eslint-phi-error-rules.test.ts` test the root ESLint config (rules defined
in `eslint.config.mjs`), not anything inside `apps/web/`. They are tooling
tests, not app tests.

**Fix:** move to `__tests__/eslint/` at repo root, add a `vitest.config.ts`
shim if needed for the root test runner. Update `pnpm test` to surface them.

### A.6 — D-number-in-source policy decision (1h)

`feedback_code_naming_and_comment_discipline` bans M-numbers, Wave-N, agent
names, ticket IDs from source. The META-2 CI gate enforces that. But
**D-numbers (D67, D148, etc.) are everywhere in source** — they map to the
strategy doc and are arguably permanent identifiers. Currently they're
un-policed: not banned, not blessed.

**Decision needed:**

- **Option A (recommended):** D-numbers are permanent strategy-doc citations,
  blessed in source. Update `scripts/meta-policy.json` to explicitly
  allowlist `D[0-9]+` in source comments. Add a META-policy entry to
  `docs/runbook/meta-2-enforcement.md` documenting the bless.
- **Option B:** ban D-numbers in source the same way M-numbers are banned.
  Force every D-citation to live in commit messages / ADRs only. Requires
  a mass-edit sweep across `apps/web/` + `packages/`.

The Option A path is the right call — D-numbers map to a versioned
strategy doc that ships with the codebase, unlike Wave-N or agent names
which are ephemeral session context. Codify and move on.

## 6. Workstream B — Enterprise-seam locks (~22-27h)

The 7 retrofit-expensive decisions. Each lands as: ADR + minimal skeleton +
test surface. Activation defers to its own trigger. All 7 are parallel-safe
after B.1 (which seeds the `@quilty/api-client` package the others may
reference).

### B.1 — HTTP client + OpenAPI codegen tooling pick (4-6h) — **HIGHEST RETROFIT COST**

Every M5/M6/M7 feature talks HTTP to the Rust backend. Pick wrong and the
call sites multiply before the rewrite cost compounds.

**Locks in shape:**

- Codegen tool: research `openapi-typescript` vs `orval` vs `kubb` vs `hey-api`
  against criteria (vendor maturity, output ergonomics, runtime weight, Zod
  integration, Rust-backend OpenAPI compat — the spec emitter ships from
  `quilty-aws/lambdas/rust/crates/quilty-openapi-emitter`).
- HTTP layer: native `fetch` vs `ky` vs `undici`-fetch; recommend native +
  thin wrapper.
- Retry policy: exponential backoff + jitter + idempotency-key reuse.
- Circuit breaker: `opossum` vs custom; recommend custom (small surface,
  zero runtime dep).
- Traceparent injection: W3C `traceparent` + `baggage` per D38 + D56.
- Idempotency-Key generation: ULID per-mutation, surfaced in response
  envelope for log correlation.
- Error envelope: RFC 9457 Problem Details parser (composes with B.3).

**Deliverable:**

- ADR-0016 (HTTP client + OpenAPI codegen).
- `packages/api-client/` skeleton with `ports.ts` + `errors.ts` +
  `domain/retry.ts` + `domain/circuit-breaker.ts` + barrel.
- `@quilty/api-client` named on `workspaces`; consumed from
  `composition.server.ts` at activation.
- One contract test against an in-memory adapter (`makeInMemoryApiClient()`)
  exercising retry + circuit-breaker behavior.

### B.2 — DynamoDB single-table-vs-feature-table policy (3-4h)

Strategy doc D63 has a two-table `consent` design. Session table (D51),
idempotency keys (currently in-memory), rate-limit (in-memory), audit
(cross-repo), user-identity (cross-repo) are all designed in isolation.
At scale this means N tables, N billing lines, N cross-table query
limitations.

**Locks in shape:**

- Per-bounded-context single-table-vs-feature-table decision matrix.
- Access-pattern doc per entity: PK, SK, GSI shape, write rate, read rate,
  hot-key risk.
- Naming convention: table name format, partition-key format.
- Billing-mode policy: `PAY_PER_REQUEST` vs `PROVISIONED` per table.

**Deliverable:**

- ADR-0017 (DynamoDB data-model policy).
- `docs/architecture/dynamodb-access-patterns.md` — Rick Houlihan / Alex
  DeBrie style doc, one section per entity.
- No code change in M1.6 (the future activation per entity will reference
  the doc).

**Note on cross-repo coordination:** the `quilty_main` table lives in
`quilty-aws/app-sync/dynamodb.tf` (NOT in this repo). The website-side ACID
boundary is around website-only tables (idempotency, rate-limit, consent,
session). The policy doc covers website-owned tables; cross-repo data lives
in the Rust backend's user-profile + session-row + outbox schema, which is
already in production at M1.5.

### B.3 — RFC 9457 Problem Details registry (2h)

Strategy doc names RFC 9457 at M6. Defining the canonical problem-type set
NOW means M5/M6/M7 endpoints emit consistent envelopes from day one.

**Locks in shape:**

- Canonical type set: `validation`, `csrf`, `rate-limit`, `auth-required`,
  `consent-required`, `session-expired`, `step-up-required`, `not-found`,
  `service-unavailable`, `idempotency-key-conflict`, `precondition-failed`.
- Per-type URI: `https://my-quilty.com/problems/<slug>`.
- Sentry-context-enrichment hook: the problem type becomes a Sentry tag
  automatically via the wrapErrorReporter sanitizer.

**Deliverable:**

- `packages/api-client/src/problem-types.ts` — typed registry + parser.
- A contract test that asserts every Route Handler emits a parseable
  problem envelope on failure paths (the `/api/contact` test suite extends
  to cover this).

### B.4 — CDP-ready Analytics port shape (1-2h)

Current `Analytics.track(event)` → single adapter. The CDP pattern
(Segment / mParticle / RudderStack) routes one event to N destinations with
per-destination consent + filtering + sampling. Even if we don't adopt a
CDP now, the port shape change is cheap and prevents N-1 call-site rewrites
when Customer.io (M3) or warehouse-native analytics (M9+) activate.

**Locks in shape:**

- Port: `track(event, destinations?: AnalyticsDestination[])` — destinations
  default to `['amplitude']` (current behavior preserved).
- Per-destination consent gating: each destination has its own consent
  category requirement.
- Per-destination sampling: each destination has its own sample-rate dial.
- Wrapper composes the consent gate per-destination at the composition root.

**Deliverable:**

- `packages/observability/src/ports.ts` — port revision (small).
- `packages/observability/src/domain/wrap-analytics.ts` — wrapper extension.
- `packages/observability/src/adapters/amplitude.ts` — adapter passes
  destination filter through.
- Contract test extension covering 2-destination fan-out + per-destination
  consent decision.

### B.5 — Test data factories package (4h)

`@quilty/test-fixtures` with `faker-js` + per-domain factories. Pays back
at M3 (demo content for hero variants), M5 (portal mockup data), M6 (auth
integration testing), every subsequent feature.

**Locks in shape:**

- Factories: `PersonFactory`, `AccountFactory`, `ConsentFactory`,
  `SessionFactory`, `SubscriptionFactory`, `ContactMessageFactory`,
  `MfaEnrollmentFactory`.
- Factory shape: `make<Entity>({ ...overrides })` returns a fully-typed
  fixture; deterministic via seeded faker.
- Per-fixture validation: every factory output passes its Zod schema (so a
  schema-drift breaks the fixture, surfaces the drift at test time).

**Deliverable:**

- `packages/test-fixtures/` skeleton with the 7 factories.
- Per-factory unit test asserting Zod-schema-validity.
- Replace ad-hoc fixtures in 2-3 existing test files as a verification.

### B.6 — Image pipeline port skeleton (2-3h)

`next/image` ships fine at marketing scale. At thousands of pages with
non-engineering MDX authors editing content, image references through an
`ImagePipeline` port are the right indirection so the underlying
transformation/CDN can swap (next/image → Cloudflare Images → imgix →
ImageKit) without a content rewrite.

**Locks in shape:**

- Port: `ImagePipeline.resolve({ src, width, height, format?, quality? }) → ResolvedImage`
- Adapter: `makeNextImageAdapter()` — wraps `next/image` resolution.
- Velite content schema extension: `image:` frontmatter field validates
  via the port + emits the resolved URL at MDX render time.

**Deliverable:**

- `packages/content/src/ports/image-pipeline.ts` (or a new
  `packages/image-pipeline/` if it grows beyond a few files).
- Adapter + contract test.
- Velite config extension.

### B.7 — CloudFront Functions edge-tier harness (4-6h)

D63 already names CloudFront Function as the future home for the GPC
FORCE-OFF cookie write (currently in `proxy.ts` Lambda). At enterprise scale
the cheap-and-frequent header/cookie work belongs at PoP edges; Lambda runs
only for actual SSR.

**Locks in shape:**

- Directory: `cf-functions/` at repo root.
- Per-function file: `<name>.cff.js` (CloudFront Function source).
- Per-function deploy path in `sst.config.ts`: SST's `aws.cloudfront.Function`
  resource via `transform.cdn`.
- Contract test: each CFF unit-tested in Node (CloudFront Functions speak
  a restricted JS subset; the test stubs the runtime).
- First function: `gpc-force-off.cff.js` mirroring the cookie-write logic
  currently in `proxy.ts` (NOT activated yet — `proxy.ts` remains canonical
  until contract parity is verified end-to-end).

**Deliverable:**

- `cf-functions/` directory + first CFF.
- sst.config.ts extension (still gated by the deploy gate — no AWS calls
  in M1.6).
- Test surface for CFF parity.

## 8. Workstream D — Promoted from "defer" (~13-17h)

These were in the prior "correctly deferring" list. On second look, each
costs $0 at zero traffic and the port shape, if not locked now, forces a

### D.1 — Pagefind search adapter scaffold (3-4h)

**Why not deferred:** Pagefind generates a static client-side search index at
build time. $0 hosted cost. Activates from day one. The eventual Algolia /
Typesense / Meilisearch swap (when content volume + search-quality demands
justify the $$$) is a one-file adapter change behind the same `SearchIndex`
port.

**Locks in shape:**

- Port: `SearchIndex.query(q, opts)` → typed `SearchResult[]`.
- Adapter: `makePagefindAdapter()` — wraps the Pagefind generated bundle.
- Velite content schema extension: every MDX page emits a search-indexable
  document.
- `apps/web/app/[locale]/(marketing)/search/page.tsx` — search results page
  (gated behind a `features.ts` flag until content justifies; UI scaffold
  ships now).

### D.2 — Style Dictionary `@quilty/tokens` package skeleton (3-4h)

**Why not deferred:** Style Dictionary is a build-time toolchain. $0 runtime
cost. The Flutter app needs token parity at the M3 visual-direction lock;
the website Tailwind v4 `@theme` block is already the source of truth for
web. Extracting tokens to a separate package now (consumed by both web and
Flutter at the right trigger) means M3 visual direction iterates against a
shared primitive layer.

**Locks in shape:**

- `packages/tokens/` skeleton.
- Source: a single `tokens.json` (or `.yaml`) — primitive + semantic layer.
- Build outputs: CSS custom properties (for web), Dart constants (for
  Flutter), Tailwind v4 `@theme` directives (regenerated into
  `apps/web/app/globals.css` via Style Dictionary).
- Velite + Tailwind v4 keep current authoring shape; Style Dictionary
  generates the `@theme` block.

### D.3 — Workflow engine port shape (Step Functions adapter prep) (2-3h)

**Why not deferred:** AWS Step Functions costs $0 at zero state transitions.
DSAR export pipeline (GDPR Art 17 mandatory) + account deletion cascade

- email drip + payment dunning are all durable workflows that activate at
  M7-M8. Locking the port now means each workflow's adapter is a one-file
  addition, not a "we need to add a workflow engine" architectural debate.

**Locks in shape:**

- Port: `WorkflowEngine.start(definition, input)` →
  `WorkflowExecution` token.
- Port: `WorkflowEngine.status(token)` →
  `'running' | 'succeeded' | 'failed' | 'timed_out'`.
- Port: `WorkflowEngine.cancel(token)`.
- Adapter: `makeStepFunctionsAdapter()` — wraps AWS SDK v3 SFN client.
- Adapter: `makeInMemoryWorkflowEngine()` — fakes the state machine
  for unit tests.
- Contract test parameterized at the port boundary.

**Deliverable:**

- `packages/workflow/` skeleton (port + 2 adapters + fake).
- No workflow definitions in M1.6 (each lands with its activation).

### D.4 — Service Worker / PWA baseline (3-4h)

**Why not deferred:** Service Worker is client-side. $0 hosted cost. PWA
install is a measurable growth lever post-launch. Adding it later means
rebuilding the cache strategy from scratch; doing it now means the cache
strategy ships with the marketing pages and the install affordance is
ready when growth-marketing flips it on.

**Locks in shape:**

- Workbox-based service worker at `public/sw.js`.
- Cache strategy: cache-first for static assets, network-first for HTML

- `apps/web/components/site/InstallPrompt.tsx` — install-prompt UI
  (gated behind a `features.ts` flag until growth justifies).
- Critical: portal routes (`/account/*`) NEVER cached client-side per D31
  zero-PHI website discipline. Service worker explicitly excludes
  `/api/auth/*`, `/api/webhooks/*`, `/[locale]/account/*`.

**Why not deferred:** `size-limit` is already configured at the apps/web

# Appendix A — WorkOS: what it is, what it does for Quilty, when to adopt

## A.1 — What WorkOS actually is

WorkOS is **NOT** an Auth0 replacement. Different product category.

- **Auth0 / Cognito / Clerk** — full-stack identity providers. You can use
  any of them as your sole authentication layer (consumer signup +
  enterprise SSO + MFA + everything).
- **WorkOS** — enterprise-features-as-an-API. It assumes you already have a
  consumer auth layer (in Quilty's case Cognito) and adds the B2B enterprise
  features ON TOP OF or ALONGSIDE it.

The framing that matches Quilty's stack: **WorkOS is the enterprise B2B
seam — it does not touch consumer auth.**

## A.2 — What WorkOS products would matter for Quilty

The Rust auth backend already reserves the seams that match these products:

### A.2.1 — WorkOS SSO ($125/connection/mo after free tier)

When an employer ("Acme Corp's wellness team") wants to give their employees
Quilty access, their IT department will require: "Authentication must go
through Acme's IdP (Okta / Azure AD / Google Workspace / OneLogin / JumpCloud
/ etc.)."

- **Without WorkOS:** you build N SAML 2.0 connections + N OIDC
  connections in Cognito (Cognito supports both natively), maintain
  per-customer attribute mappings, handle per-IdP quirks.
- **With WorkOS:** you build ONE OIDC connection from Cognito to WorkOS.
  WorkOS handles the per-customer SAML/OIDC fan-out, the per-customer
  Admin Portal, the attribute mapping. Your code receives a normalized
  SSO callback with `organization_id` + `connection_type`.

**The reservation that matches:** Cognito user-pool schema attribute
`external_idp_id` is explicitly reserved for "future SAML/SCIM JIT
provisioning."

### A.2.2 — WorkOS Directory Sync / SCIM ($125/connection/mo)

When Acme Corp adds a new employee, their HR system pushes to their IdP,
which pushes to WorkOS via SCIM, which webhooks Quilty's backend with
`user.created`. Same for `user.deactivated` (employee leaves). Same for
`group.membership_added`.

- **Without WorkOS:** you build SCIM 2.0 endpoints + per-IdP quirks (Okta's
  SCIM differs from Azure AD's).
- **With WorkOS:** normalized webhooks come in. Your handler writes to
  `quilty_main` DynamoDB.

**The reservation that matches:** the `TenantId` newtype in
`quilty-core/src/identity.rs` + the `AuditContext.tenant_id` field already
carry the multi-tenant shape; current value is `TenantId::DEFAULT`. A SCIM
webhook would mint a real tenant ID + write the org-member rows.

### A.2.3 — WorkOS Admin Portal (bundled with SSO/SCIM)

Hosted UI where customer IT admins configure their SSO/SCIM connection
without you building customer-facing config UI. You send Acme Corp's IT
admin a one-time onboarding link; they configure their side; you receive
the webhook when ready.

This is **a real engineering-time saving** at the moment B2B onboarding
becomes a thing. Without it, you'd build an org-admin settings page that
walks customers through Okta/Azure SAML config — substantial UI work that
WorkOS abstracts away.

### A.2.4 — WorkOS products that do NOT fit Quilty

- **AuthKit (hosted login UI)** — duplicates Cognito Managed Login (D6).
  Cognito Managed Login is already locked.
- **User Management (hosted user db)** — duplicates `quilty_main` DDB.
  Not adopting.
- **Audit Logs** — duplicates the existing DDB Streams → Firehose →
  S3 Object Lock audit pipeline (D39 + cross-repo).
- **Fraud / Bot Detection (Radar)** — duplicates Cloudflare Turnstile +
  Cognito threat protection (D37 + D50). Not adopting.
- **Magic Link / Passwordless** — duplicates Cognito Custom Auth Challenge
  (already implemented per the cross-repo agent finding).

## A.3 — What WorkOS does NOT do for Quilty

- It doesn't replace Cognito for consumer auth.
- It doesn't manage Quilty's user database — `quilty_main` DDB stays
  source of truth.
- It doesn't issue Quilty's tokens — consumer flows use Cognito-issued
  JWTs; B2B-federated flows can use Cognito-issued JWTs with WorkOS
  identity context propagated via custom claims.
- It doesn't handle MFA for non-SSO users (Cognito does).
- It doesn't help with the Apple/Google consumer SSO buttons (Cognito
  IdP federation already handles those — `auth/identity_providers.tf`
  has them wired).

## A.4 — How WorkOS would integrate with the existing Quilty stack

Based on the cross-repo agent findings (`quilty-aws/auth/`,
`lambdas/rust/crates/`), the integration shape is unusually clean because
of seams ALREADY reserved:

### A.4.1 — Cognito-federation pattern (recommended)

Cognito federates to WorkOS via OIDC. WorkOS appears as one more Cognito
IdP alongside Google + Apple. Every employer's SSO flows
`Acme IdP → WorkOS → Cognito → Quilty`. The Rust backend receives a
Cognito-issued JWT for the federated user; SSO context (org membership,
group memberships) rides in custom claims via the
`PreTokenGeneration V2` Cognito trigger.

**Concrete changes needed at trigger time:**

1. **`quilty-aws/auth/identity_providers.tf`** — add a third
   `aws_cognito_identity_provider` resource (`provider_type = "OIDC"`,
   pointing at WorkOS). Add Terraform variable
   `enable_workos_b2b_idp = bool` for staging-vs-prod gating. **~1 day**.
2. **`quilty-aws/lambdas/rust/crates/auth-triggers/src/handlers/`** —
   extend the `PreSignUp_ExternalProvider` trigger to recognize WorkOS
   federation + populate `external_idp_id` + `TenantId` from WorkOS
   claims. Extend `post_confirmation` to write the org-membership row.
   **~2-3 days**.
3. **`quilty-aws/app-sync/dynamodb.tf`** — extend the `quilty_main` table
   key shape per the reserved `TENANT#{t}#USER#{sub}` pattern in
   `quilty-persistence/src/ddb/user_profile.rs`. **~1-2 days, depends on
   data-model complexity**.
4. **Website BFF** — add an `Organization` port + portal UI for org-aware
   surfaces (org switcher, role display, members list). Sized by the
   actual B2B feature scope at trigger time. **~5-15 days, scope-dependent**.
5. **WorkOS contract + BAA** — paperwork. **~2-4 weeks** elapsed time, ~1
   day engineering.

Total engineering: **~10-25 days at trigger**, almost entirely Rust-backend
work in `quilty-aws/`. The website-side BFF additions are smaller.

### A.4.2 — Where WorkOS DOES NOT touch Quilty's existing stack

- Consumer auth flows are untouched.
- Cognito stays the token issuer.
- `quilty_main` DDB stays the user database.
- The existing `auth.my-quilty.com` Cognito Managed Login surface remains
  for consumer signup.
- The existing Apple/Google IdP federation remains.
- The existing session model (opaque session ID + DynamoDB store) remains.
- The existing audit pipeline (DDB Streams → Firehose → S3 Object Lock)
  remains and now naturally absorbs B2B-side events because
  `AuditContext.tenant_id` already exists.

## A.5 — Cost model

- **Free tier:** up to 1M MAU on the SSO + Directory Sync products. At 0-1M
  MAU, WorkOS is essentially free.
- **SSO post-free-tier:** ~$125/connection/month per customer organization.
- **Directory Sync post-free-tier:** ~$125/connection/month per
  customer organization.
- **At 10 enterprise customers** (each with SSO + Directory Sync): ~$2500/mo.
- **At 100 enterprise customers:** ~$25K/mo.

The cost model scales with B2B revenue — every paying customer org adds
$250/mo of WorkOS cost but typically pays $1K-50K/mo for the platform. The
margin is healthy.

2. **B2B pipeline indicates 5+ customers in next 6 months** all asking
   about SSO during sales conversations.
3. **Pre-Series-A diligence** with B2B revenue in the pitch deck.
4. **First HSA broker / employer wellness partnership** lands — the

## A.7 — Pre-trigger work (TL;DR)

## A.8 — One important nuance: SSO ≠ SAML ≠ OIDC

When customer IT says "we need SSO," they almost always mean SAML 2.0.
Some modern customers (Google Workspace shops, smaller startups) use OIDC.
WorkOS abstracts the difference. Cognito-native SAML federation can
technically handle SAML directly without WorkOS, BUT:

- Per-customer SAML connection configuration in Cognito is a manual
  Terraform-or-AWS-Console operation per customer org. Not scalable
  past 3-5 customers.
- The Admin Portal UX (where customer IT configures their side) doesn't
  exist in Cognito. You'd build that UI yourself.
- WorkOS's value isn't "SAML support" — it's "the per-customer connection
  management UX + the normalization across SAML/OIDC variants."

At 1-2 enterprise customers you could plausibly skip WorkOS and configure
Cognito SAML directly. At 5+ customers WorkOS pays for itself the moment
the first IT admin emails asking how to configure their Okta connection.
